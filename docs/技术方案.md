# 读书阅读器 · 技术方案

> 版本：v0.1　日期：2026-08-30
> 对应《产品设计文档》v0.1。本文档**取代**产品文档第 4 节"技术方向"；产品范围、验收标准仍以产品文档为准。

## 1. 选型结论

| 层 | 选型 | 解决什么问题 |
|---|---|---|
| 应用外壳 | **Electron** | 独立桌面窗口、真实文件系统、可靠持久化存储 |
| UI | **React** | 书架/阅读器是典型的状态驱动 UI，组件化开发与复用 |
| 语言 | **TypeScript** | 解析、分页、书库等核心逻辑需要类型约束，重构有底 |
| 构建 | **Vite** | 开发热更新快；与 Forge 官方模板打通，免自拼配置 |
| 打包分发 | **Electron Forge** | Electron 官方维护，一站式 `package` / `make` |

配套决策：

- **当前不引入**：SQLite、Redux、后端服务、自动更新、CI/CD。唯一目标是把 **"导入 — 阅读 — 保存 — 恢复"** 做稳（对应产品文档 §7 验收标准）。
- **数据层沿用 Web 存储**：IndexedDB 存书籍与进度，localStorage 存排版设置。Electron 渲染进程的 IndexedDB 持久化在用户数据目录，**没有浏览器标签页的数据清理/回收风险**，MVP 无需数据库。
- **先 Windows**；macOS / Linux 由 Forge 同一套配置顺带覆盖，不单独投入。

## 2. 为什么是这个组合（简述）

- MVP 全部功能围绕"读本地 TXT"。Electron 恰好提供三样直接命中需求的东西：独立窗口（沉浸阅读）、对话框 + fs（选文件、读文件）、可靠持久化（不怕丢进度）。
- React + TypeScript 把核心逻辑做成可单测的纯模块，UI 只做消费——现有 `js/` 骨架已经验证了这条路（见 §8）。
- Vite + Forge 使用官方模板（`vite-typescript`），main / preload / renderer 三层由同一套 Vite 配置构建，避免"Electron 工程配置"吃掉开发时间。

## 3. 总体架构

三个进程层，职责严格分离：

```
┌──────────────────────────────────────────────┐
│ Renderer（React SPA）                         │
│   书架 / 阅读器 / 设置条                       │
│   core/ 纯逻辑：txt-parser · pager · library  │
│   IndexedDB（书籍+进度）   localStorage（设置）│
└──────────────△───────────────────────────────┘
      contextBridge 白名单 API（唯一通道）
┌──────────────▽───────────────────────────────┐
│ Preload                                       │
│   window.api = { openTextFiles() }            │
└──────────────△───────────────────────────────┘
┌──────────────▽───────────────────────────────┐
│ Main（Node）                                  │
│   窗口生命周期 · dialog.showOpenDialog · fs    │
└──────────────────────────────────────────────┘
```

安全基线（写死，不允许放松）：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`、不加载任何远程内容、渲染层 CSP 只允许自身资源。

## 4. 目录结构

> 落地说明：plugin-vite 约定产物名取入口文件名（`main.ts` → `.vite/build/main.js`），`index.html` 固定在项目根目录，因此 main/preload 为 `src/` 下的单文件入口，而非目录入口。

```
├── docs/

├── index.html                   # 渲染层入口 HTML（plugin-vite 约定位于根目录）

├── vite.main.config.ts / vite.preload.config.ts / vite.renderer.config.ts
├── src/
│   ├── main.ts                  # 主进程入口：窗口、文件对话框、fs 读取
│   ├── preload.ts               # contextBridge 白名单 API
│   ├── forge.env.d.ts           # plugin-vite 注入的 MAIN_WINDOW_VITE_* 全局类型
│   ├── core/                    # 纯逻辑，不依赖 DOM/React/Electron，Node 可直接单测

│   │   ├── pager.ts             # 翻页数学（偏移/比例/页码换算）
│   │   ├── library.ts           # 书库逻辑（存储介质可注入）
│   │   └── storage.ts           # IndexedDB 键值存储实现
│   ├── shared/
│   │   └── types.ts             # BookMeta、Settings、OpenedTextFile 等共享类型
│   └── renderer/
│       ├── main.tsx             # React 挂载入口
│       ├── App.tsx              # 书架 / 阅读器两态切换
│       ├── components/          # Bookshelf、Reader

│       ├── library.ts           # 书库单例（IndexedDB 介质）

```

单包工程，不做 monorepo。

## 5. 关键设计

### 5.1 导入 TXT（两条路径，均不依赖文件路径）

| 入口 | 链路 |
|---|---|
| 文件对话框 | Renderer 调 `window.api.openTextFiles()` → Main `dialog.showOpenDialog` + `fs.readFile` → `ArrayBuffer` 经 IPC 结构化克隆传回 |
| 拖拽文件 | Renderer 直接获得 `File` 对象，`file.arrayBuffer()` 读取，**零 IPC** |

> Electron 32 起 `File.path` 已移除。本方案刻意不依赖路径：字节流直达渲染层，中文书名、特殊路径都不出问题。

### 5.2 编码识别（UTF-8 / GBK）

现有 `js/txt-parser.js` 已实现完整策略，迁移为 TS 即可：

1. BOM 优先：UTF-8 / UTF-16 LE / UTF-16 BE；
2. 无 BOM 则 `TextDecoder('utf-8', { fatal: true })` 严格解码，失败回退 `TextDecoder('gb18030')`（覆盖 GBK 系，含生僻字，超集兼容）；
3. 解码后规整换行（`\r\n` → `\n`）、压缩连续空行、去首尾空白。

`TextDecoder` 在 Chromium 与 Node（full-icu）下行为一致，因此该模块在 Node 单测环境与 Electron 渲染层表现相同——这正是 core 层保持环境无关的价值。

### 5.3 翻页与阅读进度

- `core/pager.ts` 保持与 DOM 解耦的纯函数：滚动偏移 ↔ 进度比例换算（现有实现），React 组件只负责测量容器尺寸与驱动滚动容器。
- 进度以 **比例（0–1）** 存储：换书、改字号、改窗口大小后都能按比例恢复到大致位置，MVP 够用。按字符偏移精确定位列为迭代项。
- 渲染侧 MVP 采用"滚动容器 + 点击左右区域/方向键翻屏"，不做虚拟长列表；若超长书出现卡顿，再引入按块渲染。

### 5.4 数据模型与持久化

IndexedDB（沿用现有实现：库 `dushu-reader`，kv store）：

| Key | 内容 |
|---|---|
| `library` | 书目元数据数组：`{ id, title, addedAt, lastReadAt, progress }` |
| `book:{id}` | 全文文本 |

localStorage：排版设置（MVP：字号；主题为明亮纸张色）。

- 保存时机：翻页/滚动后 500ms 防抖写进度；`pagehide` 与窗口关闭事件兜底补写一次。
- `core/library.ts` 已按"存储可注入"设计（`{ get, set, del }` 接口），单测注入内存实现即可，无需 `fake-indexeddb`（若后续测试需要，再作为 devDependency 引入）。

### 5.5 IPC 面最小化

MVP 只暴露一个方法：

```ts
// preload
window.api.openTextFiles(): Promise<{ name: string; data: ArrayBuffer }[]>
```

主进程不碰业务数据、不写盘，攻击面最小。后续新增 IPC 必须走同一 contextBridge 白名单，禁止在渲染层直接触 Node。

## 6. 工程与脚本

基于 Forge 官方 Vite + TypeScript 模板搭建（`npx create-electron-app@latest <app> --template=vite-typescript`，renderer 侧加装 React：`react` / `react-dom` / `@vitejs/plugin-react`）。Forge 的 Vite 插件统一负责三层构建，dev 阶段自带热更新。

| 脚本 | 含义 |
|---|---|
| `npm start` | 启动桌面应用（dev，热更新）。**语义由"本地静态服务"变为"启动 Electron"，`server.js` 已退役** |
| `npm test` | `node --test`：Node 26 原生类型剥离直接跑 TS 测试，零额外测试依赖 |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run package` | 产出免安装应用目录（`out/`） |
| `npm run make` | 产出 Windows 安装包（Squirrel.Windows，附 zip） |

两个环境相关的已知问题与对策（均已固化在本仓库）：

- **Node 26 打包静默失败**：`extract-zip@2.0.1`（依赖 `yauzl@3.2.0`）在 Node ≥24.16 / ≥26.1 下解压中途静默中断（上游 [electron/forge#4277](https://github.com/electron/forge/issues/4277)）。已在 `package.json` 用 overrides 锁定 `yauzl@3.3.1` 修复。
- **Electron 二进制下载超时**：国内网络直连 GitHub Releases 易失败，用 `ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 走镜像（`npm install` 与 `npm run package` 均适用）。

Electron 版本锁定 major，升级跟随官方节奏，规避 API 破坏性变动。

## 7. 测试策略（对齐 AGENTS.md）

- **core 层单测是硬性门槛**：编码判定（内嵌十六进制字节样本，不依赖二进制 fixture）、文本规整、书名提取、翻页数学边界（空文/单页/越界）、书库增删与进度读写。
- `library.ts` 依赖注入内存 storage，在 Node 环境直接测试；`storage.ts`（IndexedDB 封装）逻辑薄，MVP 以手工验收为主，必要时引入 `fake-indexeddb`。
- UI 组件测试 v0.1 不强制，v0.2 引入 Testing Library。
- **交付门槛**：每次改动 `npm test`（目标态含 `npm run typecheck`）全绿才可提交。

## 8. 迁移步骤（从当前骨架到目标结构）

现有 `js/` 四个模块是框架无关的纯 JS，且已具备核心策略（编码回退、存储注入、DOM 解耦），是本次迁移的主要资产：

1. ✅ 技术方案落档（本篇）；
2. ✅ Forge `vite-typescript` 模板结构重建工程骨架（`src/main.ts`、`src/preload.ts`、`src/renderer/`），`server.js` 已删除（dev 服务由 Forge/Vite 承接）；
3. ✅ `js/*.js` → `src/core/*.ts`：补类型、`node --test` 单测覆盖，逻辑保持一致；
4. ✅ React 实现书架与阅读器（对齐产品文档 §5 的 v0.1 功能表）；
5. `npm run package` 产出 Windows 包（✅ 已验证可启动/导入/阅读），按产品文档 §7 三条验收标准实测（重点：GBK 数 MB 长篇、重启续读、字号持久化），安装包 `npm run make` 待跑。

## 9. 当前阶段明确不做

SQLite（IndexedDB 够用）、Redux/Zustand（useState + Context 够用）、后端服务与云同步、自动更新（v0.2+ 可接 update.electronjs.org，Forge 的 Squirrel 打包原生兼容）、多窗口、托盘、EPUB/PDF、深色主题（均见产品文档 Roadmap）。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 安装包体积与内存占用（Electron 固有） | 接受；MVP 不引入任何原生模块，避免 node-gyp 环境差异 |
| 超长网文（数十 MB）内存压力 | 全文按字符串持有可控；正文按 200 段一组分块渲染 + `content-visibility: auto`，DOM 规模有界 |
| GBK 坏字节 | `gb18030` 非严格解码，坏字节替换为 U+FFFD，不中断阅读 |
| Electron API 破坏性变动（如 `File.path` 移除） | 锁 major 版本；架构上已不依赖文件路径 |
| 中文路径 / 中文书名 | 字节流直达渲染层；路径仅在主进程用于取初始书名 |
| Node 26 下打包静默失败 | `extract-zip`/`yauzl` 上游 bug，overrides 锁 `yauzl@3.3.1`（见 §6） |
| 关闭窗口瞬间进度丢失 | 防抖 400ms 常规保存 + `pagehide` 兜底 + localStorage 同步镜像，恢复时取两存储较大值 |
